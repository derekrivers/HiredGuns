# Isolated four-view measurement preview

Run the existing Vite development server, then open `/tools/render-preview.html`:

```sh
npm run dev -- --port 5195 --strictPort
```

The preview uses the existing `FourViews` renderer, synthetic demo level and initial world through their public APIs. It never steps or mutates gameplay. A separate Canvas2D overlay displays two authored atlas frames in all four panes. `FourViews` exposes no scene insertion or statistics API, so this measures the current renderer plus a browser-composited overlay. It is not a benchmark of renderer-integrated sprite assets. No production pack is loaded, generated, accepted or installed.

The atlas is drawn with code, encoded to PNG, then decoded with `createImageBitmap`. It has two non-overlapping regions, transparent margins/gutters, a translucent interior, opaque body pixels and a common foot pivot. Frame playback alternates every 250 ms as an explicitly authored diagnostic. Dark, light and checker swatches show alpha and registration; crosshairs mark the pivot. Pixel inspection of the decoded image reports actual alpha counts, transparent gutters and bottom-edge/centre offsets relative to the pivot. Checks concern this synthetic fixture only; no historical frame timing, original binding or pack-contract acceptance follows.

“Compare both modes” runs the current renderer baseline first, then the same renderer plus the four sprite overlays. Each mode uses a warm-up interval followed by a fixed requested sample window (defaults: 500 ms warm-up, 2000 ms sample). Only complete RAF intervals wholly inside the sample window are retained. The first/last partial intervals are excluded, and the report records absolute sample-start/end/finish timestamps and the end-boundary overrun. The deadline used to stop sampling is also used to calculate overrun, avoiding differently grouped floating-point subtraction. No negative value is clamped away: early interruption retains its negative overrun and invalidates the window. Swatch/UI work shares browser scheduling in both modes; the timed CPU submission region covers `FourViews.render` and any enabled sprite overlay drawing, excluding swatch drawing. Order, thermal state and other browser load can bias comparison. There is no FPS target or automatic speed verdict.

JSON includes raw samples plus min/median/p95/p99/max/mean frame-interval and CPU-submission distributions. These are wall-clock scheduling/submission observations, not GPU-completion time. Available WebGL draw calls and submitted triangle counts are observed by wrapping the context methods before constructing `FourViews`; instanced draw instance counts are included. Counts cover all four renderer calls per frame. No private renderer field is accessed. Three `info`, GPU timing and driver-memory bytes are explicitly unavailable/null rather than fabricated. Instrumentation itself adds overhead equally to both modes.

Each measurement records viewport, device pixel ratio, renderer's existing 1.5 DPR cap, stage/pane dimensions, drawing buffer, user agent, WebGL version/renderer and actual context attributes. The context is created with the existing renderer's alpha/antialias/power settings before instrumentation. Resizing, hidden-document events, changed captured environment or an empty sample invalidate the window. A lost context immediately interrupts the active mode on the next RAF callback, prevents further sampling, and requires reloading the preview. Loss during baseline leaves an invalid baseline and a null overlay (not started); it cannot create a fresh valid zero-draw follow-on run. Native context state is checked before every mode and frame, as well as through the loss event. The benchmark does not infer physical GPU identity from a WebGL string or label software rendering as device acceptance.

“Run 3 load/dispose cycles” repeatedly closes the owned bitmap, invokes the current renderer's public `dispose`, records observed WebGL live-resource sets, rebuilds the renderer and decodes a fresh bitmap. The report retains every cycle's after-dispose and after-reload resource counts. Bitmap create/close totals and live count are explicit. Its lifecycle assessment reports retained-handle growth if subsequent after-dispose counts increase; this is not silently treated as successful resource release. WebGL deletion does not prove immediate driver memory reclamation. “Dispose atlas” clears the sprite canvases and closes the bitmap while the renderer remains active. A new benchmark requires a loaded atlas. Controls serialize loading and measurement.

The initial headless run observed five additional tracked texture handles and three framebuffer handles after each renderer rebuild/dispose cycle. Buffers, programs, shaders, renderbuffers and vertex arrays returned to zero in those snapshots; owned bitmaps closed correctly. This is a bounded disposal finding in the existing renderer/Three lifecycle, not a measured driver memory leak. The preview preserves the evidence; renderer disposal investigation requires a separately coordinated change.

“Export JSON” downloads the current measurements, lifecycle history, asset checks, settings and limitations. The preview is available through Vite development serving; the default gameplay production bundle does not add this tool as another entrypoint. Timings differ across sessions and should be retained locally with browser/host details when comparing changes. The automated browser test covers actual loading, alpha/pivot checks, both benchmark modes, JSON download, disposal/reload and absence of page errors. Synthetic screenshots are diagnostic evidence, not artwork or original-game parity.

Real-pack support is intentionally deferred. An optional future private adapter must verify the coordinator acceptance receipt, exact manifest/payload hashes, region bounds, gutters, alpha convention, pivots and frame semantics before loading a pack. This preview accepts no external pack files and grants no authority to worker manifests alone.

The smallest next task is a bounded investigation of the observed retained texture/framebuffer handles across public renderer disposal, with its owner, before repeated-load integration. An independent hardware run on the intended PC/browser/display is also pending: record viewport/DPR, export measurements and visually check four-view alpha/registration. Keep real observations separate from headless/software results. A renderer-integrated asset API requires a separately coordinated renderer change; this packet does not redesign it.
